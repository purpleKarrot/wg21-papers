# Abstract

We propose the addition of a new class template `copy_on_write<T>` to the C++
Standard Library.

`copy_on_write<T>` manages a dynamically-allocated owned object of type `T` with
shared, reference-counted ownership. Copies of a `copy_on_write<T>` share
ownership of the same underlying object when their allocators are compatible;
the object is copied when shared data is modified or allocator incompatibility
prevents sharing. With the default allocator, copying is O(1) regardless of the
size or complexity of `T`, and mutation is deferred until necessary.

Specializations of `copy_on_write` provide value semantics when the payload has
value semantics and callers follow the mutation contract. They compose well
with other standard library types such as `vector`, allowing the compiler to
correctly generate special member functions.

Access to the owned object through `operator*` and `operator->` is always
const-qualified. Mutation is supported through the `modify` member function,
which copies the shared data when necessary and provides a structured interface
for efficient in-place or constructive modification. Aliases obtained from an
action must not be used to modify the owned object after that action finishes.

# Motivation

## Expensive Copies in Composite Classes

When composite objects contain large or expensive-to-copy members, value
semantics become costly. Consider a text editor that maintains a document as a
sequence of lines:

```cpp
class document {
  std::vector<std::string> _lines;
public:
  document() = default;
  void append(std::string line) {
    _lines.push_back(std::move(line));
  }
  std::size_t line_count() const { return _lines.size(); }
};
```

If `document` objects are copied frequently (passed by value, returned from
functions, stored in containers) but modified rarely, eagerly copying all lines
on every copy is unnecessarily expensive. Sharing the underlying storage (e.g.
with `std::shared_ptr`) avoids copies but can compromise value semantics.

`copy_on_write<T>` provides a middle ground. Multiple objects share the
underlying data, paying only an atomic reference-count increment on copy. A copy
of the data is made only when one of the sharing objects needs to mutate it.

## Composing Cheaply-Copyable Types

`copy_on_write<T>` allows composite classes to be cheaply copyable even when
their components are expensive to copy:

```cpp
class document {
  std::copy_on_write<std::vector<std::string>> _lines;
public:
  document() = default;

  // Default allocator: copies share storage and do not throw.
  document(const document&) = default;
  document& operator=(const document&) = default;

  // Mutation copies the underlying data only if shared.
  void append(std::string line) {
    _lines.modify([&](std::vector<std::string>& v) {
      v.push_back(std::move(line));
    });
  }

  std::size_t line_count() const { return _lines->size(); }
};
```

The class above has full value semantics — compiler-generated copy, move, and
assignment work correctly — while avoiding expensive deep copies when the
document is only being read.

## Efficient Fork-and-Edit Patterns

`copy_on_write<T>` is well suited to fork-and-edit workflows where a derived
value is created from an existing one with few changes:

```cpp
std::copy_on_write<Config> cfg = base_config();
std::copy_on_write<Config> debug_cfg(cfg);  // O(1), shared
debug_cfg.modify([](Config& c) {
  c.set_log_level(LogLevel::Debug);
});
// cfg is unchanged; debug_cfg holds a private copy.
```

Without `copy_on_write`, the second line would require a full deep copy of
`Config` regardless of whether it is ever modified.

## Avoiding Redundant Work on Shared Data

The `identical_to` member function identifies objects that share the underlying
data. Algorithms can use this information to avoid redundant work, such as
recomputing a deterministic result from the same input, when their semantics
permit it.

# Design Requirements

## Shared Ownership with Value Semantics

Unlike `indirect<T>`, which has unique ownership, `copy_on_write<T>` uses
shared, reference-counted ownership. The reference count is maintained
atomically to allow copies to be safely shared across threads.

Despite shared ownership of the underlying storage, `copy_on_write<T>` presents
value semantics when `T` itself has value semantics and callers follow the
mutation contract: two `copy_on_write<T>` objects are equal when their owned
objects are equal, and modifying one through `modify` does not affect the other.

## A new type rather than a composable wrapper

If copy-on-write semantics could be imparted to other types using an adapter
class template, we could use `copy_on_write_adapter<indirect<T>>` or
`copy_on_write_adapter<polymorphic<T>>` to create copy-on-write types. This
adapter class could be used similarly to container adapters such as `queue`,
`stack` and `priority_queue`.

Implementing copy-on-write behaviour requires intrusion into the details of
object ownership and is not possible to implement for `indirect<T>` or
`polymorphic<T>` without adding an additional layer of indirection.

To support polymorphic copy-on-write behaviour, an additional class,
`polymorphic_copy_on_write` would be required. We are not proposing addition of
this class template in this proposal.

## Cheap Copies

With the default allocator, copying a `copy_on_write<T>` increments the
reference count and shares a pointer to the owned object. The cost is O(1) and
independent of the size or complexity of `T`. Shared data is copied when
`modify` is called. With other allocators, copying also copies the owned object
if allocator incompatibility prevents sharing.

## Read-Only Access via Observers

`copy_on_write<T>` provides only const access to the owned object through
`operator*` and `operator->`. This avoids handing out mutable references through
the observers. The action invoked by `modify` receives a mutable reference after
detachment if necessary, but the callable interface cannot prevent the caller
from retaining that reference. Correctness therefore also depends on the
mutation contract described below.

When a `copy_on_write<T>` is accessed through a const access path, constness
propagates to the owned object. Because all access is already const-qualified,
this is automatically satisfied.

## Modification Through `modify`

Modification of the owned object is performed through the `modify` member
function. Two overloads are provided:

**`modify(action)`** accepts a callable of the form `void(T&)`. If the reference
count is one (exclusive ownership), the action is applied directly to the owned
object. If the reference count exceeds one (shared ownership), the owned object
is first copied, ownership becomes exclusive, and then the action is applied.

**`modify(action, transform)`** accepts both a `void(T&)` action and a
`T(T const&)` transformation. If the reference count is one, the action is
applied in-place. If the reference count exceeds one, a new owned object is
constructed by calling the transformation on the current value, without first
copying the old value. This allows the caller to provide an optimised
construction path for the shared case.

For example, when inserting an element at the front of a vector: the in-place
action calls `insert` on the existing vector; the transformation constructs a
new vector from scratch, placing the new element first and then appending the
remaining elements. In the shared case this avoids the cost of first copying the
full vector and then inserting.

Mutable access obtained from an action, including pointers, iterators, and views
into the owned object, may be used to modify the object only while that action
is executing. This restriction also applies if the action exits by throwing an
exception. During a `modify` invocation, the wrapper being modified must not be
copied from, moved from, assigned to, swapped, destroyed, or passed to another
`modify` invocation. The transformation must not modify its input object.

## Identity Optimisation

The `identical_to` member function returns `true` when two objects of the same
specialisation share the same owned object. Users may call it to short-circuit
work in algorithms when the semantics of those algorithms permit it.

Storage identity does not imply that the owned object compares equal to itself.
For example, a floating-point NaN compares unequal to itself, and its three-way
comparison with itself yields `partial_ordering::unordered`. The same issue can
arise in composite types containing floating-point values or in user-defined
comparisons. The relational operators therefore compare the owned values even
when storage is shared, preserving the payload's comparison semantics.

## The Valueless State and Interaction with `std::optional`

`copy_on_write<T>` has a valueless state used to implement move. A
`copy_on_write<T>` object becomes valueless only after it has been moved from.
Accessing the owned object of a valueless object is undefined behaviour. The
`valueless_after_move` member function returns `true` if the object is in the
valueless state.

The valueless state is not intended to be observable in normal use. There is no
`operator bool` or `has_value` member function.

Where a nullable `copy_on_write<T>` is required,
`std::optional<copy_on_write<T>>` is recommended.

## Allocator Support

`copy_on_write<T>` is allocator-aware. The allocator is used to allocate and
deallocate storage for an internal control block that holds both the reference
count and the owned object.

Copy construction selects the destination allocator using
`select_on_container_copy_construction`; copy assignment follows
`propagate_on_container_copy_assignment`. A copy shares the underlying data
when the resulting destination allocator compares equal to the source
allocator. Otherwise, a deep copy is made using the destination allocator.
This ensures that an object created with one memory resource is not owned by
another incompatible resource.

## Special Member Functions

`copy_on_write<T>` is suitable for use as a member of composite classes where
the compiler will generate special member functions. Copy construction and copy
assignment are available whenever `T` is copy constructible and have conditional
`noexcept` specifications based on the allocator. Both are non-throwing with
the default allocator. Move construction is unconditionally available and
noexcept.

# Prior Work

The copy-on-write idiom has a long history in C++. Qt's `QSharedDataPointer`
[@QT] pioneered a reusable COW pointer type in a major C++ framework. Adobe's
`stlab` library provides a `copy_on_write` type along similar lines [@STLAB].
The GCC implementation of `std::basic_string` prior to C++11 used copy-on-write
semantics internally; it was later removed due to incompatibilities with the
C++11 memory model and iterator invalidation requirements.

This proposal standardises a modern, allocator-aware formulation aligned with
the design of `std::indirect` [@P3019R14].

# Impact on the Standard

This proposal is a pure library extension. It requires additions to be made to
the standard library header `<memory>`.

## X.Y Class template copy_on_write [cow]

### X.Y.1 General [cow.general]

- A `copy_on_write` object manages the lifetime of an owned object. A
  `copy_on_write` object is _valueless_ if it has no owned object. A
  `copy_on_write` object may become valueless only after it has been moved from.

- Multiple `copy_on_write` objects may share ownership of the same owned object.
  A reference count is maintained to track the number of objects sharing
  ownership. The reference count is modified atomically. When the reference
  count reaches zero, the owned object is destroyed and its storage is
  deallocated.

- Mutable access to an owned object or its subobjects obtained from an action
  invoked by `modify` shall not be used to modify those objects after that
  action invocation completes, whether normally or by throwing an exception.
  This requirement includes access through retained references, pointers,
  iterators, or views.

- In every specialization `copy_on_write<T, Allocator>`, if the type
  `allocator_traits<Allocator>::value_type` is not the same type as `T`, the
  program is ill-formed. Every object of type `copy_on_write<T, Allocator>` uses
  an object of type `Allocator` to allocate and free storage for the owned
  object as needed.

- A program that instantiates the definition of the template
  `copy_on_write<T, Allocator>` with a non-object type, an array type,
  `in_place_t`, a specialization of `in_place_type_t`, or a cv-qualified type
  for the `T` parameter is ill-formed.

- The template parameter `T` of `copy_on_write` may be an incomplete type.
  [The destructor requires `T` to be complete ([cow.dtor]). Defining
  a constructor of an enclosing class can require instantiating that destructor
  ([class.base.init]{.sref}).]{.note}

- The template parameter `Allocator` of `copy_on_write` shall meet the
  _Cpp17Allocator_ requirements.

- If a program declares an explicit or partial specialization of
  `copy_on_write`, the behavior is undefined.

The following exposition-only concepts are used in the specification. Let `F` be
a type and `T` a value type.

- _`cow-action<F, T>`_ is satisfied when `F` is invocable with an lvalue of type
  `T` and the result type is `void`.

- _`cow-transformation<F, T>`_ is satisfied when `F` is invocable with a const
  lvalue of type `T` and the result type is `T`.

```cpp
    allocator_arg_t, const Allocator& a,

  explicit constexpr copy_on_write(
    allocator_arg_t, const Allocator& a,

    noexcept(
      allocator_traits<Allocator>::is_always_equal::value);

  explicit constexpr copy_on_write(
    allocator_arg_t, const Allocator& a,
    copy_on_write&& other)
    noexcept(
      allocator_traits<Allocator>::is_always_equal::value);

  constexpr copy_on_write(const copy_on_write& other) noexcept(see below);

  constexpr copy_on_write& operator=(const copy_on_write& other)

    const copy_on_write& other) const noexcept;

  template <class F>  // requires cow-action<F, T>
  constexpr void modify(F&& f);

  template <class F, class G>

    //       && cow-transformation<G, T>

 private:
  Allocator alloc = Allocator();  // exposition only
  /* unspecified */ p;            // exposition only
};
```

### X.Y.3 Constructors [cow.ctor]

_Throws_: Nothing unless `allocator_traits<Allocator>::allocate`,

```cpp
explicit constexpr copy_on_write(
  allocator_arg_t, const Allocator& a,
  const copy_on_write& other)
  noexcept(
    allocator_traits<Allocator>::is_always_equal::value);
```

- _Mandates_: `is_copy_constructible_v<T>` is `true`.
- _Effects_: `alloc` is direct-non-list-initialized with `a`. If `other` is
  valueless, `*this` is valueless. Otherwise, if `a == other.alloc` is `true`,
  `*this` shares ownership of `other`'s owned object and the reference count is
  incremented. Otherwise, constructs an owned object of type `T` with `*other`,
  using the allocator `alloc`.

```cpp
explicit constexpr copy_on_write(
  allocator_arg_t, const Allocator& a,
  copy_on_write&& other)
  noexcept(
    allocator_traits<Allocator>::is_always_equal::value);
```

- _Effects_: `alloc` is direct-non-list-initialized with `a`. If `other` is
  valueless, `*this` is valueless. Otherwise, if `a == other.alloc` is `true`,
  `*this` takes exclusive ownership of the owned object of `other`. Otherwise,
  constructs an owned object of type `T` with `std::move(*other)`, using the
  allocator `alloc`.
- _Postconditions_: `other` is valueless.

```cpp
constexpr copy_on_write(const copy_on_write& other) noexcept(see below);
```

- _Mandates_: `is_copy_constructible_v<T>` is `true`.
- _Effects_: `alloc` is direct-non-list-initialized with
  `allocator_traits<Allocator>::select_on_container_copy_construction(other.alloc)`.
  If `other` is valueless, `*this` is valueless. Otherwise, if
  `alloc == other.alloc` is `true`, `*this` shares ownership of `other`'s owned
  object and the reference count is incremented. Otherwise, constructs an owned
  object of type `T` with `*other`, using the allocator `alloc`.
- _Remarks_: Let `S` be `true` if the expression
  `a.select_on_container_copy_construction()` is not well-formed for a const
  lvalue `a` of type `Allocator`; otherwise, let `S` be
  `noexcept(a.select_on_container_copy_construction())`. The exception
  specification is equivalent to
  `noexcept(allocator_traits<Allocator>::is_always_equal::value && S)`.

```cpp
constexpr copy_on_write(copy_on_write&& other) noexcept;
```

- _Effects_: `alloc` is direct-non-list-initialized with `other.alloc`. If
  `other` is valueless, `*this` is valueless. Otherwise, `*this` takes exclusive
  ownership of the owned object of `other`.
- _Postconditions_: `other` is valueless.

### X.Y.4 Destructor [cow.dtor]

```cpp
constexpr ~copy_on_write();
```

- _Mandates_: `T` is a complete type.
- _Effects_: Decrements the reference count of the owned object. If the
  reference count reaches zero, destroys the owned object using
  `allocator_traits<Allocator>::destroy` and deallocates the storage.

### X.Y.5 Assignment [cow.assign]

```cpp
constexpr copy_on_write& operator=(const copy_on_write& other)
  noexcept(
    allocator_traits<Allocator>
      ::propagate_on_container_copy_assignment::value
    || allocator_traits<Allocator>
         ::is_always_equal::value);
```

- _Mandates_: `is_copy_constructible_v<T>` is `true`.

- _Effects_: If `addressof(other) == this` is `true`, there are no effects.
  Otherwise:

  1. The allocator needs updating if
     `allocator_traits<Allocator>::propagate_on_container_copy_assignment::value`
     is `true`.

  2. If `other` is valueless, `*this` becomes valueless.

  3. Otherwise, if the allocator needs updating or
     `alloc == other.alloc` is `true`, `*this` shares ownership of `other`'s
     owned object. The reference count is incremented.

  4. Otherwise, constructs a new owned object of type `T` with `*other`, using
     the allocator `alloc`.

  5. The reference count of the previously-owned object in `*this`, if any, is
     decremented; if it reaches zero, the owned object is destroyed and storage
     is deallocated.

  6. If the allocator needs updating, the allocator in `*this` is replaced with
     a copy of the allocator in `other`.

- _Returns_: A reference to `*this`.

```cpp
constexpr copy_on_write& operator=(copy_on_write&& other)
  noexcept(
    allocator_traits<Allocator>
      ::propagate_on_container_move_assignment::value
    || allocator_traits<Allocator>::is_always_equal::value);
```

- _Effects_: If `addressof(other) == this` is `true`, there are no effects.
  Otherwise:

  1. The allocator needs updating if
     `allocator_traits<Allocator>::propagate_on_container_move_assignment::value`
     is `true`.

  2. If `other` is valueless, `*this` becomes valueless. The reference count of
     the previously-owned object in `*this`, if any, is decremented; if it
     reaches zero, the owned object is destroyed and storage is deallocated.

  3. Otherwise, if the allocator does not need updating and
     `alloc == other.alloc` is `true`, `*this` takes exclusive ownership of the
     owned object of `other`.

  4. Otherwise, constructs a new owned object with `std::move(*other)`, using
     the allocator `alloc`.

  5. The reference count of the previously-owned object in `*this`, if any, is
     decremented; if it reaches zero, the owned object is destroyed and storage
     is deallocated.

  6. If the allocator needs updating, the allocator in `*this` is replaced with
     a copy of the allocator in `other`.

- _Postconditions_: `other` is valueless.

- _Returns_: A reference to `*this`.

```cpp
template <class U = T>
constexpr copy_on_write& operator=(U&& u);
```

- _Constraints_:
  - `is_same_v<remove_cvref_t<U>, copy_on_write>` is `false`,
  - `is_constructible_v<T, U>` is `true`, and
  - `is_assignable_v<T&, U>` is `true`.
- _Effects_: If `*this` is not valueless and `use_count() == 1`, equivalent to
  `**this = std::forward<U>(u)`. Otherwise, constructs a new `copy_on_write<T>`
  from `std::forward<U>(u)` and move-assigns it to `*this`.
- _Returns_: A reference to `*this`.

### X.Y.6 Observers [cow.obs]

```cpp
constexpr const T& operator*() const noexcept;
```

- _Preconditions_: `*this` is not valueless.
- _Returns_: A const reference to the owned object.

```cpp
constexpr const_pointer operator->() const noexcept;
```

- _Preconditions_: `*this` is not valueless.
- _Returns_: A pointer to the owned object.

```cpp
constexpr bool valueless_after_move() const noexcept;
```

- _Returns_: `true` if `*this` is valueless, otherwise `false`.

```cpp
constexpr allocator_type get_allocator() const noexcept;
```

- _Returns_: `alloc`.

```cpp
constexpr long use_count() const noexcept;
```

- _Preconditions_: `*this` is not valueless.
- _Returns_: The number of `copy_on_write` objects currently sharing ownership
  of the owned object.
- _Remarks_: In the presence of concurrent access, the returned value may be
  stale by the time it is observed. It should be treated as an optimisation hint
  rather than a precise count.

```cpp
constexpr bool identical_to(const copy_on_write& other) const noexcept;
```

- _Preconditions_: Neither `*this` nor `other` is valueless.
- _Returns_: `true` if `*this` and `other` share the same underlying owned
  object, otherwise `false`.

### X.Y.7 Modifiers [cow.mod]

The following element applies to both `modify` overloads:

- _Preconditions_: During the invocation, `*this` is not copied from, moved
  from, assigned to, swapped, destroyed, or the subject of another invocation of
  `modify`.

```cpp
template <class F>  // requires cow-action<F, T>
constexpr void modify(F&& f);
```

- _Constraints_: _`cow-action<F, T>`_ is satisfied.
- _Preconditions_: `*this` is not valueless.
- _Effects_: If `use_count() == 1`, calls `std::forward<F>(f)` with a mutable
  reference to the owned object. Otherwise, creates a new owned object as a copy
  of the current owned object (using the allocator `alloc`), decrements the
  reference count of the previous owned object, takes exclusive ownership of the
  new object, and calls `std::forward<F>(f)` with a mutable reference to the new
  owned object.

```cpp
template <class F, class G>
  // requires cow-action<F, T> && cow-transformation<G, T>
constexpr void modify(F&& f, G&& g);
```

- _Constraints_: _`cow-action<F, T>`_ and _`cow-transformation<G, T>`_ are both
  satisfied.
- _Preconditions_: `*this` is not valueless. The invocation of `g`, if any, does
  not modify the owned object passed to it.
- _Effects_: If `use_count() == 1`, calls `std::forward<F>(f)` with a mutable
  reference to the owned object. Otherwise, creates a new owned object by
  calling `std::forward<G>(g)` with a const reference to the current owned
  object (using the allocator `alloc`), decrements the reference count of the
  previous owned object, and takes exclusive ownership of the new object.
- _Remarks_: In the shared case, the transformation `g` is responsible for
  constructing the new value. Unlike the single-argument `modify(action)`
  overload, the old owned object is not copied before the new one is created;
  `g` receives only a const reference. This allows callers to construct the new
  value more efficiently than copy-then-modify.

### X.Y.8 Swap [cow.swap]

```cpp
constexpr void swap(copy_on_write& other)
  noexcept(
    allocator_traits<Allocator>
      ::propagate_on_container_swap::value
    || allocator_traits<Allocator>::is_always_equal::value);
```

- _Preconditions_: If
  `allocator_traits<Allocator>::propagate_on_container_swap::value` is `false`,
  then `get_allocator() == other.get_allocator()` is `true`.
- _Effects_: Exchanges the owned objects or valueless states of `*this` and
  `other`. If `allocator_traits<Allocator>::propagate_on_container_swap::value`
  is `true`, the allocators of `*this` and `other` are exchanged. Otherwise the
  allocators are not swapped. [Does not call `swap` on the owned
  objects directly.]{.note}

```cpp
template <class T, class A>
constexpr void swap(
  copy_on_write<T, A>& lhs,
  copy_on_write<T, A>& rhs)
  noexcept(noexcept(lhs.swap(rhs)));
```

- _Effects_: Equivalent to `lhs.swap(rhs)`.

### X.Y.9 Relational operators [cow.relops]

```cpp
template <class U, class AA>
friend constexpr bool operator==(
  const copy_on_write& lhs,
  const copy_on_write<U, AA>& rhs)
  noexcept(noexcept(*lhs == *rhs));
```

- _Mandates_: The expression `*lhs == *rhs` is well-formed and its result is

- _Returns_: If `lhs` is valueless or `rhs` is valueless,


- _Returns_: If `lhs` is valueless or `rhs` is valueless,
  `!lhs.valueless_after_move() <=> !rhs.valueless_after_move()`. Otherwise,
  `synth-three-way(*lhs, *rhs)`.

# Design Discussions

## Read-Only Access and the `modify` Interface

The absence of a non-const `operator*` and `operator->` is the most distinctive
aspect of `copy_on_write` compared to `indirect`.

Providing a `T&` directly could detach the shared object before returning the
reference. However, the reference could remain alive while subsequent copies
of the wrapper start sharing that object, allowing mutation of shared state.

The `modify` interface makes the intended scope of mutable access explicit. It
determines at the point of invocation whether a copy is needed (when
`use_count() > 1`) or whether in-place modification is safe (when
`use_count() == 1`). It does not enforce that scope: a callback can retain a
mutable alias or copy the wrapper before finishing its mutations.

For example, both of the following violate the mutation contract:

```cpp
std::copy_on_write<int> value(1);
int* escaped = nullptr;
value.modify([&](int& n) { escaped = &n; });
auto other = value;
*escaped = 2;  // Mutable access used after the action finishes.
```

```cpp
std::copy_on_write<int> value(1);
std::optional<std::copy_on_write<int>> other;
value.modify([&](int& n) {
  other.emplace(value);  // Copies the wrapper during modify.
  n = 2;
});
```

The restrictions cover aliases into subobjects as well as the `T&` passed to the
action, and apply on exceptional exit too. Const observers do not recursively
enforce constness through pointers stored inside `T`, and detachment does not
provide a deeper copy than `T`'s own copy semantics. The payload remains
responsible for its own value semantics.

The two-argument overload `modify(action, transform)` further allows callers to
provide a more efficient algorithm for the shared case. When ownership is not
exclusive and the old object must be discarded, constructing the new value from
scratch (via `transform`) is often more efficient than copy-constructing and
then modifying. The caller is in the best position to provide this optimisation.

## Atomic Reference-Count Performance

Repeated calls to `modify` can require repeated atomic uniqueness checks, even
when a wrapper was just constructed and has not been copied. Such checks can
also inhibit optimizations of the payload work. The reference implementation
includes benchmarks comparing separate mutation calls, grouped mutations,
direct construction, and mutation of shared values.

When intermediate observations and exception behavior permit, related changes
can be grouped into one action:

```cpp
lines.modify([](std::vector<std::string>& value) {
  value.reserve(100);
  value.push_back("first");
  value.push_back("second");
});
```

For initial setup, callers can construct the final payload directly with an
in-place constructor or prepare it locally and move it into `copy_on_write`.
Grouping requires one uniqueness check for the action; constructing the final
payload directly avoids mutation-time checks during setup. A shared value still
requires detachment, and a payload-specific transformation can reduce the cost
of producing the new value.

Measurements on one macOS arm64 system with Apple Clang 21 and Clang 23 show
that grouping improves the larger setup batches in the benchmark, but can be
slower for small batches. Preparing a local value and moving it into the wrapper
also incurs a payload-dependent cost. These results support offering batching
and direct construction as techniques to measure, rather than promising that
one approach is always faster.

Single-threaded diagnostic probes also show that replacing an atomic counter
with a plain counter can improve some workloads, but does not uniformly improve
all tested cases. These probes do not provide the wrapper's full ownership and
thread-safety semantics. The measurements do not yet justify adding a counter
customization parameter to the proposed interface. The proposal retains atomic
reference counting; representative application workloads, other architectures,
and concurrent ownership would need evaluation before pursuing customization.

## Thread Safety

Subject to the mutation contract and the usual thread-safety requirements on
`T`, the reference count is maintained with atomic operations, making it safe
to copy and destroy distinct `copy_on_write<T>` objects concurrently from
different threads. Concurrent reads of the owned object are safe only in the
usual sense: multiple threads may call `operator*` and `operator->`
simultaneously on objects sharing the same underlying data. Concurrent calls to
`modify` on distinct objects that share data are safe; the first caller to
modify will detach its copy, leaving the other objects undisturbed.

Concurrent calls to `modify` on the _same_ `copy_on_write<T>` object, or
concurrent read and write of the same object, require external synchronisation,
as with any mutable standard library type.

## Interaction with `shared_ptr`

`copy_on_write<T>` has a similar ownership model to `shared_ptr<const T>`:
multiple owners, atomic reference counting. It differs in several important
respects:

- The observers provide only const access. Mutable access provided to a
  `modify` action is subject to the mutation contract.
- Mutation is performed through the first-class `modify` interface rather than
  being entirely absent.
- `copy_on_write` has value semantics: it is copy-assignable and participates in
  value-based equality comparison and hashing.
- `copy_on_write` has no null state and does not support pointer arithmetic or
  custom deleters.
- `copy_on_write` is allocator-aware in the standard manner.

## `use_count` and `identical_to`

`use_count` and `identical_to` expose internal sharing state and are provided
primarily as optimisation hints, analogous to `shared_ptr::use_count`. Their
values may change concurrently when other objects sharing the same data are
copied or destroyed. Programs should not rely on the exact value of `use_count`
for correctness in the presence of concurrent access.

`identical_to` provides an O(1) check for shared storage. It is distinct from
value equality and is not used internally to bypass payload comparisons.

## Copy Exception Guarantees and Allocator Compatibility

Ordinary copy construction and copy assignment are conditionally `noexcept`.
With `std::allocator<T>`, both operations share storage without allocating or
copying `T`, and neither throws. Defaulted copy operations in a composite class
inherit this guarantee when its other members also support non-throwing copies.

The guarantee cannot apply to every allocator specialization while retaining
conventional allocator-aware behavior. Copy construction selects an allocator
using `select_on_container_copy_construction`. Selection may throw, and it may
return an allocator unequal to the source allocator. In the latter case, a new
owned object must be allocated and copied. For example, a
`pmr::polymorphic_allocator` selects the default memory resource on copy
construction, which may differ from the source resource. Copy assignment can
likewise require a deep copy when unequal allocators do not propagate.

For ordinary copy construction, `is_always_equal` guarantees that allocator
selection cannot prevent sharing. The exception specification also accounts
for whether the allocator's selection member, if present, is declared
non-throwing. If that member is absent, selection copies the allocator, an
operation that the allocator requirements guarantee does not throw. The
specification tests the optional member rather than the exception specification
of `allocator_traits::select_on_container_copy_construction`, which is not
conditionally `noexcept`. The allocator-extended copy constructor does not
perform selection, so its exception specification depends only on
`is_always_equal`.

Copy assignment is non-throwing when either the allocator propagates on copy
assignment or `is_always_equal` is `true`. Both cases permit sharing, and
propagating allocator copy assignment is required not to throw. Equality of
particular allocator instances also permits sharing, but cannot strengthen the
exception specification, which is a property of the type.

An alternative would require all ordinary copies to share storage and be
unconditionally `noexcept`. Preserving the existing allocator model would then
require stronger allocator requirements that exclude useful stateful allocator
configurations, including general `pmr` use. Alternatively, allocator selection
and propagation semantics would need to change. This proposal retains
conventional allocator behavior and exposes the guarantees available through
conditional `noexcept`. The O(1) copy guarantee applies when storage is shared;
allocator-incompatible copies incur allocation and the cost of copying `T`.

## Constant Evaluation

The constructors, destructor, assignment operators, observers, modifiers,
comparisons, and swap operations are `constexpr`. This allows sharing and
copy-on-write mutation within constant evaluation, provided the operations on
`T`, the allocator, and any invoked callable are permitted in constant
expressions. Hashing additionally depends on the constant-evaluation support
of `hash<T>`.

```cpp
static_assert([] {
  std::copy_on_write<int> original(42);
  auto changed = original;
  changed.modify([](int& value) { ++value; });
  return *original == 42 && *changed == 43
      && !original.identical_to(changed);
}());
```

## Incomplete Types and Out-of-Line Special Members

`copy_on_write<T>` can be declared with an incomplete `T`, but its destructor
requires `T` to be complete. This supports a class whose implementation is
forward-declared in a header and defined in a source file, provided the relevant
special members are defined where the implementation type is complete.

An inline defaulted move constructor of the enclosing class can instantiate
its `copy_on_write` member's destructor. In a non-delegating constructor, the
destructors of potentially constructed subobjects are potentially invoked
([class.base.init]{.sref}), even when the constructor is `noexcept`. Declaring
the enclosing destructor out of line does not by itself avoid this issue.
Move assignment also has to release the destination's previous owned object.

The portable pattern is to declare the enclosing special members in the header
and default them after the implementation type is defined:

```cpp
// document.h
class document {
  struct implementation;
  std::copy_on_write<implementation> impl_;
public:
  document();
  document(const document&);
  document& operator=(const document&);
  document(document&&) noexcept;
  document& operator=(document&&) noexcept;
  ~document();
};

// document.cpp
struct document::implementation { /* ... */ };
document::document() = default;
document::document(const document&) = default;
document& document::operator=(const document&) = default;
document::document(document&&) noexcept = default;
document& document::operator=(document&&) noexcept = default;
document::~document() = default;
```

An alternative is to permit destruction with incomplete `T` by storing a
destruction callback in a control block whose layout does not depend on `T`.
The callback is established where `T` is complete. This can support inline
moves with the default allocator, at the cost of callback storage and an
indirect call when the last owner releases the object. Supporting the full
allocator model also requires separating allocator-compatible moves from
paths that allocate and copy `T`; erased destruction alone is insufficient.

This proposal retains the complete-type requirement for destruction, consistent
with `indirect` ([indirect.dtor]{.sref}), and uses out-of-line special members
for this pattern. It does not require erased destruction or guarantee inline
defaulted moves of enclosing classes with incomplete payloads.

## Explicit Constructors

All constructors of `copy_on_write` are marked `explicit`. Using
dynamically-allocated shared storage is a deliberate choice that should not
occur implicitly. This is consistent with the design of `indirect` and
`polymorphic` [@P3019R14].

## Interaction with `indirect`

`copy_on_write<T>` and `indirect<T>` are complementary vocabulary types for
dynamically-allocated values:

| Property | `indirect<T>` | `copy_on_write<T>` |
| --- | --- | --- |
| Ownership | Unique | Shared (COW) |
| Copy cost | Cost of copying `T` | O(1) when sharing; otherwise allocation and copying `T` |
| Mutable access | Yes | Via `modify` only |
| `use_count` | No | Yes |
| `identical_to` | No | Yes |
| Const propagation | Yes | Yes (always const) |
| Allocator-aware | Yes | Yes |

Prefer `indirect<T>` when mutation is frequent and sharing is not expected.
Prefer `copy_on_write<T>` when copies are frequent, mutations are rare, or
sharing can be exploited for efficiency.

# Appendix A: Before and After Examples

We show how `copy_on_write` simplifies composite class design and reduces copy
overhead in a text-editor document model.

## Without `copy_on_write`

```cpp
// document.h

class document {
  std::vector<std::string> _lines;
public:
  document() = default;

  // Deep copy required — O(number of lines).
  document(const document&) = default;
  document& operator=(const document&) = default;

  document(document&&) noexcept = default;
  document& operator=(document&&) noexcept = default;

  void append(std::string line) {
    _lines.push_back(std::move(line));
  }

  void insert(std::size_t pos, std::string line) {
    _lines.insert(_lines.begin() + pos, std::move(line));
  }

  void erase(std::size_t pos) {
    _lines.erase(_lines.begin() + pos);
  }

  std::size_t line_count() const { return _lines.size(); }

  const std::string& line(std::size_t i) const {
    return _lines[i];
  }
};
```

## After, using `copy_on_write`

```cpp
// document.h

class document {
  std::copy_on_write<std::vector<std::string>> _lines;
public:
  document() = default;

  // Default allocator: copies share storage and do not throw.
  document(const document&) = default;
  document& operator=(const document&) = default;

  document(document&&) noexcept = default;
  document& operator=(document&&) noexcept = default;

  void append(std::string line) {
    _lines.modify(
      [&](std::vector<std::string>& v) {
        v.push_back(std::move(line));
      });
  }

  void insert(std::size_t pos, std::string line) {
    _lines.modify(
      // In-place: exclusive ownership.
      [&](std::vector<std::string>& v) {
        v.insert(v.begin() + pos, line);
      },
      // Constructive: shared ownership, no prior copy.
      [&](const std::vector<std::string>& v) {
        std::vector<std::string> w;
        w.reserve(v.size() + 1);
        w.insert(w.end(), v.begin(), v.begin() + pos);
        w.push_back(std::move(line));
        w.insert(w.end(), v.begin() + pos, v.end());
        return w;
      });
  }

  void erase(std::size_t pos) {
    _lines.modify(
      [&](std::vector<std::string>& v) {
        v.erase(v.begin() + pos);
      },
      [&](const std::vector<std::string>& v) {
        std::vector<std::string> w;
        w.reserve(v.size() - 1);
        w.insert(w.end(), v.begin(), v.begin() + pos);
        w.insert(w.end(), v.begin() + pos + 1, v.end());
        return w;
      });
  }

  std::size_t line_count() const { return _lines->size(); }

  const std::string& line(std::size_t i) const {
    return (*_lines)[i];
  }

  // Check whether two documents share their line storage.
  bool shares_data_with(const document& other) const {
    return _lines.identical_to(other._lines);
  }
};
```

The `insert` and `erase` operations demonstrate the two-argument `modify`
overload: when the document's lines are exclusively owned, the in-place action
is used; when the lines are shared, the constructive transform builds a new
vector from scratch, avoiding a redundant copy followed by a mutation.

The `shares_data_with` method demonstrates `identical_to`. Two documents that
have not yet diverged will return `true`, allowing an editor to skip redundant
display refreshes or diffs.
