# Abstract

This paper proposes `std::copy_on_write<T, Allocator>`, an allocator-aware type
for values that are copied frequently and modified infrequently. It allows
copies to share an owned object and defers copying that object until mutation
requires a separate value.

The observers `operator*` and `operator->` provide const access. `modify(f)`
invokes `f` on the exclusively owned object or on a new copy if ownership is
shared. `modify(f, g)` uses `g` to construct a replacement in the shared case,
avoiding a copy followed by modification.

# Motivation

## Expensive Copies in Composite Classes

When composite objects contain large or expensive-to-copy members, value
semantics become costly. Consider a text editor that maintains a document as a
sequence of lines:

```cpp
class document {
  std::vector<std::string> _lines;
public:
  document() = default;
  void append(std::string line) {
    _lines.push_back(std::move(line));
  }
  std::size_t line_count() const { return _lines.size(); }
};
```

Copying a `document` copies all its lines, even if neither document is later
modified. Sharing mutable storage through `std::shared_ptr` avoids that copy,
but allows changes to one document to affect another.

With `copy_on_write<T>` and the default allocator, copies share storage.
Modifying a shared value through `modify` constructs a separate object,
leaving the other copies unchanged.

## Composing Cheaply-Copyable Types

`copy_on_write<T>` allows composite classes to be cheaply copyable even when
their components are expensive to copy:

```cpp
class document {
  std::copy_on_write<std::vector<std::string>> _lines;
public:
  document() = default;

  // Mutation copies the underlying data only if shared.
  void append(std::string line) {
    _lines.modify([&](std::vector<std::string>& v) {
      v.push_back(std::move(line));
    });
  }

  std::size_t line_count() const { return _lines->size(); }
};
```

The class has value semantics with compiler-generated copy and move operations.
Copies share the line storage; modifying one document does not change another.

## Efficient Fork-and-Edit Patterns

An independently editable configuration can initially share the original's
storage:

```cpp
std::copy_on_write<Config> cfg = base_config();
std::copy_on_write<Config> debug_cfg(cfg);  // O(1), shared
debug_cfg.modify([](Config& c) {
  c.set_log_level(LogLevel::Debug);
});
// cfg is unchanged; debug_cfg holds a private copy.
```

Copying a `Config` directly would invoke its copy constructor immediately.
Here, copying the underlying `Config` is deferred until `debug_cfg` is modified.

## Avoiding Redundant Work on Shared Data

The `identical_to` member function identifies objects that share the underlying
data. Algorithms can use this information to avoid redundant work, such as
recomputing a deterministic result from the same input, when their semantics
permit it.

# Design Requirements

## Shared Ownership with Value Semantics

Unlike `indirect<T>`, which has unique ownership, `copy_on_write<T>` uses
shared, reference-counted ownership. It provides value semantics when `T` has
value semantics and callers follow the mutation contract: comparison uses the
owned values, and modifying one copy through `modify` does not affect another.

## A Separate Type

An adaptor over `indirect<T>` or `polymorphic<T>` cannot share their owned
objects through their public interfaces. It would need another layer of
indirection to provide shared ownership. This proposal instead provides a
separate type that manages sharing directly. Polymorphic copy-on-write is
outside its scope.

## Cheap Copies

With the default allocator, copy construction of a `copy_on_write<T>` increments
the reference count and shares a pointer to the owned object. The cost is O(1) and
independent of the size or complexity of `T`. With other allocators, copying
the wrapper also copies the owned object if allocator incompatibility prevents
sharing. Modification copies a shared object or uses the caller-supplied
transformation to construct its replacement; exclusive ownership permits
in-place modification.

Copy assignment acquires shared ownership in constant time when the allocators
permit sharing. Releasing the destination's previous ownership can additionally
require destruction and deallocation.

## Read-Only Access via Observers

`operator*` and `operator->` provide only const access to the owned object.
The action invoked by `modify` receives a mutable reference. Since a callable
can retain that reference, callers must follow the mutation contract below.

## Modification Through `modify`

`modify` has two overloads:

**`modify(action)`** accepts a callable of the form `void(T&)`. With exclusive
ownership, it applies the action to the owned object. With shared ownership,
it copies the object and applies the action to the copy. The wrapper takes
ownership of that copy only after the action returns normally.

**`modify(action, transform)`** accepts both a `void(T&)` action and a
`T(T const&)` transformation. With exclusive ownership, it applies the action
in place. With shared ownership, it constructs a replacement from the result
of the transformation, without first copying the old value.

To make the resulting value independent of sharing, the caller should provide
an action and transformation that perform the same logical modification.
Equivalence is not a precondition: different modifications produce a result
that depends on whether ownership is exclusive.

For example, to erase an element from a vector, the action can call `erase`,
while the transformation constructs a vector containing only the retained
elements. This avoids copying the element to be erased and then shifting the
following elements.

In the shared case, both overloads retain ownership of the original object if
allocation, construction, or the invoked callable throws. Its value is unchanged
provided operations on `T` and the allocator do not modify it as a side effect.
In the exclusive case, mutation is performed in place, so the payload's
exception guarantee is determined by the action. Providing an unconditional
strong exception guarantee would generally require making a backup copy even
when ownership is exclusive.

Mutable access obtained from an action, including pointers, iterators, and views
into the owned object, may be used to modify the object only while that action
is executing. This restriction also applies if the action exits by throwing an
exception. During a `modify` invocation, the wrapper being modified must not be
copied from, moved from, assigned to, swapped, destroyed, or passed to another
`modify` invocation. In the shared case, neither callable may modify the
original object or its subobjects, including through captured aliases.

Assignment from a value through `operator=(U&&)` can also modify the owned
object in place when ownership is exclusive. During that assignment, the
wrapper is subject to the same reentrancy restrictions. Mutable aliases
obtained during assignment to the owned object must not be used to modify it
after that assignment finishes, whether normally or by throwing an exception.

## Identity Optimisation

The `identical_to` member function returns `true` when two objects of the same
specialisation share the same owned object. Users may call it to short-circuit
work in algorithms when the semantics of those algorithms permit it.

Storage identity does not imply that the owned object compares equal to itself.
For example, a floating-point NaN compares unequal to itself, and its three-way
comparison with itself yields `partial_ordering::unordered`. The same issue can
arise in composite types containing floating-point values or in user-defined
comparisons. The relational operators therefore compare the owned values even
when storage is shared, preserving the payload's comparison semantics.

## The Valueless State and Interaction with `std::optional`

`copy_on_write<T>` has a valueless state used to implement move. A
`copy_on_write<T>` object can be valueless after it has been moved from,
constructed or assigned from a valueless object, or swapped with a valueless
object.
Accessing the owned object of a valueless object is undefined behaviour. The
`valueless_after_move` member function returns `true` if the object is in the
valueless state.

The valueless state is not intended to be observable in normal use. There is no
`operator bool` or `has_value` member function.

Where a nullable `copy_on_write<T>` is required,
`std::optional<copy_on_write<T>>` is recommended.

## Allocator Support

`copy_on_write<T>` is allocator-aware. The allocator is used to allocate and
deallocate storage for the owned object and the reference-counting state,
either directly or through rebinding. Their storage layout is unspecified.

Copy construction selects the destination allocator using
`select_on_container_copy_construction`; copy assignment follows
`propagate_on_container_copy_assignment`. A copy shares the underlying data
when the resulting destination allocator compares equal to the source
allocator. Otherwise, a deep copy is made using the destination allocator.
This ensures that an object created with one memory resource is not owned by
another incompatible resource.

## Special Member Functions

`copy_on_write<T>` is suitable for use as a member of composite classes where
the compiler will generate special member functions. Copy construction and copy
assignment are available whenever `T` is copy constructible and have conditional
`noexcept` specifications based on the allocator. Both are non-throwing with
the default allocator. Move construction is unconditionally available and
noexcept.

# Prior Work

The copy-on-write idiom has a long history in C++. Qt's `QSharedDataPointer`
[@QT] pioneered a reusable COW pointer type in a major C++ framework. Adobe's
`stlab` library provides a `copy_on_write` type along similar lines [@STLAB].
The GCC implementation of `std::basic_string` prior to C++11 used copy-on-write
semantics internally; it was later removed due to incompatibilities with the
C++11 memory model and iterator invalidation requirements.

This proposal standardises a modern, allocator-aware formulation aligned with
the design of `std::indirect` [@P3019R14].

# Impact on the Standard

This proposal is a pure library extension. It requires additions to be made to
the standard library header `<memory>`.

## X.Y Class template `copy_on_write` [cow] {#cow -}

### X.Y.1 General [cow.general] {#cow.general -}

::: wording
[#]{.pnum} A `copy_on_write` object manages the lifetime of an owned object. A
`copy_on_write` object is _valueless_ if it has no owned object. A
`copy_on_write` object is valueless only if it has been moved from, constructed
from a valueless object, assigned a valueless object, or swapped with a
valueless object.

[#]{.pnum} Multiple `copy_on_write` objects may share ownership of the same owned object.
A reference count is maintained to track the number of objects sharing
ownership. Acquiring shared ownership of an object increments its reference
count.

[#]{.pnum} Releasing ownership of an object decrements its reference count.
If the reference count reaches zero, the owned object is destroyed using
`allocator_traits<Allocator>::destroy` and its storage is deallocated.

[#]{.pnum} Transferring ownership of an object from one `copy_on_write` object
to another makes the source valueless without changing the reference count.
[Other `copy_on_write` objects can continue to share ownership of the
transferred object.]{.note}

[#]{.pnum} Operations on distinct `copy_on_write` objects that share ownership
shall not introduce data races through shared internal storage, including
allocator objects stored there ([res.on.data.races]).

[#]{.pnum} A `copy_on_write` object has _exclusive ownership_ of its owned object
if it is not valueless and no other `copy_on_write` object shares ownership of
that object.

[#]{.pnum} On normal return from an operation that constructs a new owned
object, `*this` has exclusive ownership of that object.

[#]{.pnum} A release of ownership of an object happens before
([intro.races]) any subsequent determination of exclusive ownership of that
object by `modify` or `operator=(U&&)`. That determination happens before
invocation of the action or assignment to the owned object, respectively.
Every release of ownership of an object happens before destruction of that
object.

[#]{.pnum} These ordering requirements are unaffected by intervening ownership
transfers or swaps.
[Neither ownership transfer, `swap`, nor `use_count` itself provides
synchronization between threads.]{.note}

[#]{.pnum} If a program uses mutable access obtained during an invocation of
an action by `modify` to modify the object passed to that action or any of its
subobjects after the action invocation completes, the behavior is undefined.
The same applies to mutable access obtained during assignment to the owned
object by `operator=(U&&)` and used to modify that object or any of its
subobjects after that assignment completes. Completion includes both normal
return and exit via an exception.
[Such access can be retained through references, pointers, iterators, or
views.]{.note}

[#]{.pnum} In every specialization `copy_on_write<T, Allocator>`, if the type
`allocator_traits<Allocator>::value_type` is not the same type as `T`, the
program is ill-formed. Every object of type `copy_on_write<T, Allocator>` uses
an object of type `Allocator` to allocate and free storage for the owned
object as needed.

[#]{.pnum} Memory allocation performed by member functions uses `$alloc$` or an allocator
obtained by rebinding `$alloc$` to an unspecified type. Storage is deallocated
using an allocator that compares equal to the allocator used to allocate it.
[The reference count and owned object can be stored in a single allocation
or in separate allocations.]{.note}

[#]{.pnum} Constructing an object of type `T` with `args...` using the allocator `a`
means calling `allocator_traits<Allocator>::construct(a, $p$, args...)`, where
`args` is an expression pack, `a` is an allocator of type `Allocator`, and
`$p$` is a pointer of type `T*` to storage suitable for an object of type `T`
within an allocation obtained using `a` or an allocator obtained by rebinding
`a`. Destroying an owned object uses
`allocator_traits<Allocator>::destroy` with an allocator of type `Allocator`
that compares equal to the allocator used to construct the object.

[#]{.pnum} The allocator `$alloc$` may be replaced only via assignment or `swap`.
Allocator replacement is performed only if the corresponding trait
`allocator_traits<Allocator>::propagate_on_container_copy_assignment::value`,
`allocator_traits<Allocator>::propagate_on_container_move_assignment::value`,
or `allocator_traits<Allocator>::propagate_on_container_swap::value` is `true`
within the implementation of the corresponding operation
([container.reqmts]).

[#]{.pnum} A program that instantiates the definition of the template
`copy_on_write<T, Allocator>` with a non-object type, an array type,
`in_place_t`, a specialization of `in_place_type_t`, or a cv-qualified type
for the `T` parameter is ill-formed.

[#]{.pnum} The template parameter `T` of `copy_on_write` may be an incomplete type.
[The destructor requires `T` to be complete ([[cow.dtor]](#cow.dtor)). Defining
a constructor of an enclosing class can require instantiating that destructor
([class.base.init]).]{.note}

[#]{.pnum} The template parameter `Allocator` of `copy_on_write` shall meet the
_Cpp17Allocator_ requirements.

[#]{.pnum} If a program declares an explicit or partial specialization of
`copy_on_write`, the behavior is undefined.

[#]{.pnum} The following exposition-only concepts are used in the specification:

```cpp
namespace std {
  template<class F, class T>
  concept $cow-action$ =                                      // exposition only
    invocable<F, T&> && same_as<invoke_result_t<F, T&>, void>;

  template<class F, class T>
  concept $cow-transformation$ =                              // exposition only
    invocable<F, const T&> && same_as<invoke_result_t<F, const T&>, T>;
}
```

# Design Discussions

## Non-Intrusive Reference Counting and Storage Adoption

`copy_on_write<T>` does not require `T` to contain a reference counter, derive
from a particular base class, or provide reference-counting operations. It can
therefore be used with existing payload types that meet the requirements of the
requested operations, including standard containers and types whose definition
the caller cannot change. The payload's representation and copy semantics
remain independent of the wrapper's ownership bookkeeping.

An intrusive design places the counter in the payload, or requires the payload
to provide a protocol for managing it. Such a design can support adoption of an
existing allocation when that allocation already participates in the required
ownership and destruction protocol. It requires cooperation from the payload;
using a type without that protocol may require an additional wrapper. Copying
the payload must also establish the appropriate reference count for the new
object rather than copy its existing ownership count.

This proposal provides no operation to adopt an existing `T*` or to release the
owned allocation. Constructing `copy_on_write<T>` from an existing value
constructs a new owned `T` using the allocator; it does not take ownership of
the source object's storage. Moving a payload such as a vector can transfer its
internal buffer efficiently, but the owned vector object itself is still newly
constructed. The reference implementation stores the counter and payload in
one allocation, so non-intrusive reference counting need not imply a separate
allocation for the counter. The proposal does not prescribe that layout.

Adopting arbitrary storage would require specifying its reference-counting
state, compatible allocator and destruction mechanism, and the treatment of
existing mutable aliases. An intrusive counter alone does not address those
aliases or establish value semantics. The proposed interface favors use with
existing payload types and allocator-aware construction; storage adoption
would require a separate interface and contract.

## Read-Only Access and the `modify` Interface

The absence of a non-const `operator*` and `operator->` is the most distinctive
aspect of `copy_on_write` compared to `indirect`.

Providing a `T&` directly could detach the shared object before returning the
reference. However, the reference could remain alive while subsequent copies
of the wrapper start sharing that object, allowing mutation of shared state.

The `modify` interface makes the intended scope of mutable access explicit. It
determines at the point of invocation whether ownership is shared or exclusive,
including the synchronization required for in-place modification. This
determination is independent of the public `use_count` observer. The interface
does not enforce that scope: a callback can retain a
mutable alias or copy the wrapper before finishing its mutations.

For example, both of the following violate the mutation contract:

```cpp
std::copy_on_write<int> value(1);
int* escaped = nullptr;
value.modify([&](int& n) { escaped = &n; });
auto other = value;
*escaped = 2;  // Mutable access used after the action finishes.
```

```cpp
std::copy_on_write<int> value(1);
std::optional<std::copy_on_write<int>> other;
value.modify([&](int& n) {
  other.emplace(value);  // Copies the wrapper during modify.
  n = 2;
});
```

The restrictions cover aliases into subobjects as well as the `T&` passed to the
action, and apply on exceptional exit too. In the shared case, neither callable
may modify the original object through another access path, such as a captured
alias or a cast that removes constness from an observer's result. Otherwise,
modifying the replacement could also change the value seen by other owners.
Const observers do not recursively
enforce constness through pointers stored inside `T`, and detachment does not
provide a deeper copy than `T`'s own copy semantics. The payload remains
responsible for its own value semantics.

Value assignment has the same restrictions because it can invoke a
user-defined assignment operator on the exclusively owned object. That
assignment operator must not copy or reenter the wrapper while modifying the
payload, or retain mutable aliases for later mutation.

The two-argument overload lets the caller construct the replacement directly
when copying and then modifying would do redundant work. Equivalent changes
in the two branches make the resulting value independent of sharing. This is
usage guidance, not a precondition: the overload specifies each branch without
requiring a value-equivalence relation on `T` or equivalent side effects from
the callables. In particular, the branches can allocate differently or throw
under different conditions.

The action must return exactly `void`: `modify` does not return a result, and
this requirement avoids silently discarding one. The transformation must
return exactly `T`, rather than a reference or a type convertible to `T`, to
express construction of a replacement value. These are deliberate interface
restrictions; accepting and discarding arbitrary action results or converting
transformation results would be possible alternative designs.

The transformation's result is passed to `allocator_traits<Allocator>::construct`
([allocator.traits.members]). With the default allocator, it is forwarded as
an xvalue to construct the owned object. Guaranteed copy elision therefore does
not eliminate the requirement to construct `T` from `T&&`. This explains the
`is_move_constructible_v<T>` mandate, which also admits a copy constructor that
accepts an rvalue. This overload does not require copying the old value; the
one-argument overload requires copy construction to detach it.

In the shared case, the replacement is committed only after the action, or the
transformation and construction of its result, succeeds. Const observers of the
wrapper therefore continue to refer to the original owned object during the
callback. Failure preserves ownership and storage identity. Preserving the
value additionally depends on operations on `T` and the allocator not changing
the original object as a side effect. For example, a copy constructor can
modify a `mutable` subobject of its source before throwing. Side effects on
other objects are not rolled back.

## Atomic Reference-Count Performance

Repeated calls to `modify` can require repeated atomic uniqueness checks, even
when a wrapper was just constructed and has not been copied. Such checks can
also inhibit optimizations of the payload work.

When intermediate observations and exception behavior permit, related changes
can be grouped into one action:

```cpp
lines.modify([](std::vector<std::string>& value) {
  value.reserve(100);
  value.push_back("first");
  value.push_back("second");
});
```

For initial setup, callers can construct the final payload directly with an
in-place constructor or prepare it locally and move it into `copy_on_write`.
Grouping requires one uniqueness check for the action; constructing the final
payload directly avoids mutation-time checks during setup. A shared value still
requires detachment, and a payload-specific transformation can reduce the cost
of producing the new value.

## Thread Safety

Multiple threads may read or copy from the same `copy_on_write<T>` object.
Mutation, moving from it, swapping, and destruction require synchronization
with other accesses to that wrapper.

Distinct wrappers can be used concurrently even when they share an owned
object. The implementation orders accesses preceding release of ownership
before subsequent exclusive mutation and destruction, including across moves
and swaps. Atomicity of the reference count alone would not suffice.

Callers must follow the mutation contract. Operations on `T`, callbacks, and
user-supplied allocation resources must support the concurrent uses made of
them. For example, a const member function that updates a mutable cache may
need synchronization.

An observer's reference or pointer neither retains ownership nor prevents
mutation. Reading through it requires an owner that remains alive and
unmodified throughout the read, or synchronization with mutation and
destruction of the owned object.

## Interaction with `shared_ptr`

`copy_on_write<T>` has a similar ownership model to `shared_ptr<const T>`:
multiple owners, atomic reference counting. It differs in several important
respects:

- The observers provide only const access. Mutable access provided to a
  `modify` action is subject to the mutation contract.
- Mutation is performed through the first-class `modify` interface rather than
  being entirely absent.
- `copy_on_write` has value semantics: it is copy-assignable and participates in
  value-based equality comparison and hashing.
- `copy_on_write` provides no public constructor for an empty state. Its
  valueless state arises from moving or propagation of a valueless state.
  Custom deleters are not supported.
- `copy_on_write` is allocator-aware in the standard manner.

## `use_count` and `identical_to`

`use_count` and `identical_to` expose internal sharing state and are provided
primarily as optimisation hints, analogous to `shared_ptr::use_count`. The value
of `use_count` may change concurrently when other objects sharing the same data
are copied or destroyed. Programs should not rely on its exact value for
correctness in the presence of concurrent access.

The implementation's determination of exclusive ownership for `modify` and
value assignment supplies the synchronization needed to modify the owned
object in place. Calling `use_count()` does not supply that synchronization,
even when its result is `1`.

`identical_to` provides an O(1) check for shared storage. It is distinct from
value equality and is not used internally to bypass payload comparisons.
Copying or destroying other owners does not change the result of `identical_to`
for two wrappers whose owned objects remain unchanged.

## Copy Exception Guarantees and Allocator Compatibility

Copy construction and copy assignment are conditionally `noexcept`. With
`std::allocator<T>`, both operations acquire shared ownership in O(1) time
without allocating or copying `T`, and neither throws. Copy assignment can
additionally destroy the destination's previous owned object and deallocate
its storage when the destination was its last owner. Defaulted copy operations
in a composite class inherit the non-throwing guarantee when its other members
also support non-throwing copies.

Allocator selection during ordinary copy construction may throw or produce an
allocator incompatible with the source, requiring allocation and copying of
`T`. For example, `pmr::polymorphic_allocator` selects the default memory
resource, which may differ from the source resource. Copy assignment can
likewise require a deep copy when unequal allocators do not propagate.
Retaining an additional allocator in the shared control block for destruction
and deallocation does not change these allocator-selection and sharing rules.

Making copies unconditionally `noexcept` would require restricting supported
allocators or changing allocator selection and propagation semantics. This
proposal retains conventional allocator-aware behavior and expresses the
available guarantees through conditional `noexcept`. The O(1) guarantee applies
to acquiring shared ownership; incompatible allocators incur allocation and
the cost of copying `T`. Assignment additionally incurs any cost of releasing
the destination's previous ownership.

## Constant Evaluation

The constructors, destructor, assignment operators, observers, modifiers,
comparisons, and swap operations are `constexpr`. This allows sharing and
copy-on-write mutation within constant evaluation, provided the operations on
`T`, the allocator, and any invoked callable are permitted in constant
expressions. Hashing additionally depends on the constant-evaluation support
of `hash<T>`.

Related work on constant evaluation of shared ownership is presented in
[@P3037R4]. This proposal does not require `shared_ptr` itself to become
`constexpr`: `copy_on_write` can implement its ownership and lifetime management
directly, as the reference implementation does.

```cpp
static_assert([] {
  std::copy_on_write<int> original(42);
  auto changed = original;
  changed.modify([](int& value) { ++value; });
  return *original == 42 && *changed == 43
      && !original.identical_to(changed);
}());
```

## Incomplete Types and Out-of-Line Special Members

`copy_on_write<T>` can be declared with an incomplete `T`, but its destructor
requires `T` to be complete. This supports a class whose implementation is
forward-declared in a header and defined in a source file, provided the relevant
special members are defined where the implementation type is complete.

An inline defaulted move constructor of the enclosing class can instantiate
its `copy_on_write` member's destructor. In a non-delegating constructor, the
destructors of potentially constructed subobjects are potentially invoked
([class.base.init]), even when the constructor is `noexcept`. Declaring
the enclosing destructor out of line does not by itself avoid this issue.
Move assignment also has to release the destination's previous owned object.

The portable pattern is to declare the enclosing special members in the header
and default them after the implementation type is defined:

```cpp
// document.h
class document {
  struct implementation;
  std::copy_on_write<implementation> impl_;
public:
  document();
  document(const document&);
  document& operator=(const document&);
  document(document&&) noexcept;
  document& operator=(document&&) noexcept;
  ~document();
};

// document.cpp
struct document::implementation { /* ... */ };
document::document() = default;
document::document(const document&) = default;
document& document::operator=(const document&) = default;
document::document(document&&) noexcept = default;
document& document::operator=(document&&) noexcept = default;
document::~document() = default;
```

An alternative is to permit destruction with incomplete `T` by storing a
destruction callback in a control block whose layout does not depend on `T`.
The callback is established where `T` is complete. This can support inline
moves with the default allocator, at the cost of callback storage and an
indirect call when the last owner releases the object. Supporting the full
allocator model also requires separating allocator-compatible moves from
paths that allocate and copy `T`; erased destruction alone is insufficient.

This proposal retains the complete-type requirement for destruction, consistent
with `indirect` ([indirect.dtor]), and uses out-of-line special members
for this pattern. It does not require erased destruction or guarantee inline
defaulted moves of enclosing classes with incomplete payloads.

## Explicit Constructors

All constructors of `copy_on_write` other than the ordinary copy and move
constructors are marked `explicit`. Using dynamically-allocated shared storage
is a deliberate choice that should not occur implicitly. Explicit value
construction follows the design of `indirect` and `polymorphic` [@P3019R14].

## Interaction with `indirect`

`copy_on_write<T>` and `indirect<T>` are complementary vocabulary types for
dynamically-allocated values:

| Property | `indirect<T>` | `copy_on_write<T>` |
| --- | --- | --- |
| Ownership | Unique | Shared (COW) |
| Copy construction cost | Cost of copying `T` | O(1) when sharing; otherwise allocation and copying `T` |
| Copy assignment cost | Payload-dependent | Cost of acquiring ownership plus any destruction and deallocation of the previous owned object |
| Mutable access | Yes | Via `modify` only |
| `use_count` | No | Yes |
| `identical_to` | No | Yes |
| Const propagation | Yes | Yes (always const) |
| Allocator-aware | Yes | Yes |

Prefer `indirect<T>` when mutation is frequent and sharing is not expected.
Prefer `copy_on_write<T>` when copies are frequent, mutations are rare, or
sharing can be exploited for efficiency.

# Appendix A: Before and After Examples

We show how `copy_on_write` simplifies composite class design and reduces copy
overhead in a text-editor document model.

## Without `copy_on_write`

```cpp
// document.h

class document {
  std::vector<std::string> _lines;
public:
  document() = default;

  // Deep copy required — O(number of lines).
  document(const document&) = default;
  document& operator=(const document&) = default;

  document(document&&) noexcept = default;
  document& operator=(document&&) noexcept = default;

  void append(std::string line) {
    _lines.push_back(std::move(line));
  }

  void insert(std::size_t pos, std::string line) {
    _lines.insert(_lines.begin() + pos, std::move(line));
  }

  void erase(std::size_t pos) {
    _lines.erase(_lines.begin() + pos);
  }

  std::size_t line_count() const { return _lines.size(); }

  const std::string& line(std::size_t i) const {
    return _lines[i];
  }
};
```

## After, using `copy_on_write`

```cpp
// document.h

class document {
  std::copy_on_write<std::vector<std::string>> _lines;
public:
  document() = default;

  // Default allocator: copies share storage and do not throw.
  document(const document&) = default;
  document& operator=(const document&) = default;

  document(document&&) noexcept = default;
  document& operator=(document&&) noexcept = default;

  void append(std::string line) {
    _lines.modify(
      [&](std::vector<std::string>& v) {
        v.push_back(std::move(line));
      });
  }

  void insert(std::size_t pos, std::string line) {
    _lines.modify(
      // In-place: exclusive ownership.
      [&](std::vector<std::string>& v) {
        v.insert(v.begin() + pos, line);
      },
      // Constructive: shared ownership, no prior copy.
      [&](const std::vector<std::string>& v) {
        std::vector<std::string> w;
        w.reserve(v.size() + 1);
        w.insert(w.end(), v.begin(), v.begin() + pos);
        w.push_back(std::move(line));
        w.insert(w.end(), v.begin() + pos, v.end());
        return w;
      });
  }

  void erase(std::size_t pos) {
    _lines.modify(
      [&](std::vector<std::string>& v) {
        v.erase(v.begin() + pos);
      },
      [&](const std::vector<std::string>& v) {
        std::vector<std::string> w;
        w.reserve(v.size() - 1);
        w.insert(w.end(), v.begin(), v.begin() + pos);
        w.insert(w.end(), v.begin() + pos + 1, v.end());
        return w;
      });
  }

  std::size_t line_count() const { return _lines->size(); }

  const std::string& line(std::size_t i) const {
    return (*_lines)[i];
  }

  // Check whether two documents share their line storage.
  bool shares_data_with(const document& other) const {
    return _lines.identical_to(other._lines);
  }
};
```

The `insert` and `erase` operations demonstrate the two-argument `modify`
overload: when the document's lines are exclusively owned, the in-place action
is used; when the lines are shared, the constructive transform builds a new
vector from scratch, avoiding a redundant copy followed by a mutation.

The `shares_data_with` method demonstrates `identical_to`. Two documents that
have not yet diverged will return `true`, allowing an editor to skip redundant
display refreshes or diffs.
